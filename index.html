Generator (python3 gen.py out.pdf N)
Code, 15 lines
import sys
n = int(sys.argv[2])
kids = b" ".join(b"%d 0 R" % (3 + 2 * i) for i in range(n))
objs = [b"<< /Type /Catalog /Pages 2 0 R >>", b"<< /Type /Pages /Kids [%s] /Count %d >>" % (kids, n)]
for i in range(n):
    objs.append(b"<< /Type /Page /Parent 2 0 R /MediaBox [0 0 100 100] /Contents %d 0 R >>" % (4 + 2 * i))
    objs.append(b"<< /Length 1 >>\nstream\n0 0 m 100 100 l S")
out = bytearray(b"%PDF-1.7\n"); offs = []
for i, o in enumerate(objs, 1):
    offs.append(len(out)); out += b"%d 0 obj\n%s\nendobj\n" % (i, o)
x = len(out)
out += b"xref\n0 %d\n0000000000 65535 f \n" % (len(objs) + 1)
out += b"".join(b"%010d 00000 n \n" % o for o in offs)
out += b"trailer\n<< /Size %d /Root 1 0 R >>\nstartxref\n%d\n%%%%EOF\n" % (len(objs) + 1, x)
open(sys.argv[1], "wb").write(out)

Cause. When Stream::read can't read a stream at its /Length, parse_fallback searches for stream and then for endstream in the whole rest of the file (object/stream.rs), not in the object being read. For a dictionary, the first search finds a later object's stream. If endstream is missing, the second search runs to the end of the file and fails, once per such stream.

The xref rebuild reaches this fallback for every dictionary with a /Type, which is a separate fix (related: №2).

Fix. Ending both searches at the object's endobj would fix both: object 4 would find no stream, and each search would read only its own object. In my fork this is fixed as part of a rewrite of how objects are read, so a PR for main would be new code; happy to write one.

2 hayro-syntax: rebuilding the xref table reads every typed dictionary as a stream, so it is quadraticsmall
Fix on our branch 89139436, 069c71cf
PR branch pr/rebuild-reads-typed-dicts-as-streams
Files repro/hayro-rebuild-reads-typed-dicts-as-streams

Rebuilding the xref table costs the number of dictionaries with a /Type times the length of the file after them.

Reproduction. A file of N annotation dictionaries, no streams, and a startxref that points nowhere (generator below), Pdf::new plus pages():

N file main (af0dc88) with the swap below
4,000 271 KB 4.94 G instructions 34 M
8,000 543 KB 19.7 G 68 M
16,000 1.1 MB 79.2 G (3.3 s) 136 M

Cause. fallback_xref_map_inner reads every dictionary that has a /Type as a Stream, and only then checks whether it is an /ObjStm (xref.rs). A dictionary without a stream has no /Length, so Stream::read falls back to searching the rest of the file for stream and endstream (related: №1).

Fix. Check the type first; nothing else uses the stream read there:

-                        if let Some(stream) = old_r.read::<Stream<'_>>(&dummy_ctx)
-                            && dict.get::<Name<'_>>(TYPE).as_deref() == Some(b"ObjStm")
+                        if dict.get::<Name<'_>>(TYPE).as_deref() == Some(b"ObjStm")
+                            && let Some(stream) = old_r.read::<Stream<'_>>(&dummy_ctx)

That alone still reads an /ObjStm dictionary that has no stream as a stream: many of them keep the rebuild quadratic, and one of them takes the data of a later stream as its own. So also read it as a stream only when the stream keyword follows, as Object::read does. Our branch pr/rebuild-reads-typed-dicts-as-streams does both on main at 036fb21c: two commits, 9 lines in xref.rs, and a test that the later stream is not taken. Happy to open the PR.

3 hayro-syntax: rebuilding the xref table is quadratic in the number of << inside an unterminated stringpart of a redesign
Fix on our branch 069c71cf
Files repro/hayro-rebuild-unterminated-strings-quadratic

When the xref table is rebuilt, each << inside an unterminated string costs a read of the rest of the file. A 128 KB file takes a third of a second, and the time grows with the square of the size.

Reproduction. One object holding << /A ( N times, and a startxref that points nowhere (generator below), Pdf::new plus pages() on main at af0dc88:

N file instructions
4,000 32 KB 952 M
8,000 64 KB 3.79 G
16,000 128 KB 15.1 G (0.35 s)
Generator (python3 gen.py out.pdf N) 
# One object holding n unterminated `<< /A (`, with a startxref that points nowhere, so the table is rebuilt.
import sys
n = int(sys.argv[2])
out = bytearray(b"%PDF-1.7\n1 0 obj\n<< /Type /Catalog /Pages 2 0 R >>\nendobj\n"
                b"2 0 obj\n<< /Type /Pages /Kids [3 0 R] /Count 1 >>\nendobj\n"
                b"3 0 obj\n<< /Type /Page /Parent 2 0 R /MediaBox [0 0 100 100] >>\nendobj\n")
out += b"4 0 obj\n" + b"<< /A ( " * n + b"\nendobj\n"
out += b"trailer\n<< /Size 5 /Root 1 0 R >>\nstartxref\n999999999\n%%EOF\n"

Cause. fallback_xref_map_inner probes every << it meets with probe_dict (xref.rs). Inside a string that never ends, the probe reads to the end of the file and fails. The scan then moves on by one token and probes the next << in the same string.

Fix. I don't have a small fix to offer. In my fork the rebuild became one forward pass that reads each object to its end once (069c71c), which is a rewrite of the scan rather than a patch. Happy to help with whichever direction you prefer.

4 hayro-syntax: each xref section's trailer is parsed over the sections nested inside it, so opening a file can cost 256 times its sizemoderate
Fix on our branch f8384eb1
Files repro/hayro-xref-nested-sections-quadratic

Opening a file whose xref sections lie inside each other's trailers costs the number of sections times the file size. A 100 MB file would take about 19 s by extrapolation (not run), where one section reads in milliseconds.

Reproduction. N sections chained by /Prev, each inside a /S ( string of the trailer before it, with a pad of a bytes in the innermost string (generator below), Pdf::new plus pages() on main at af0dc88:

N 1 MB pad 4 MB pad
1 48 M instructions 189 M
64 1.04 G
128 2.06 G
256 4.13 G (0.19 s) 16.3 G

The cap holds the factor at 256: at N = 257 the chain is rejected after 256 sections and the table is rebuilt (4.21 G in all).

Generator (python3 gen.py out.pdf N [pad])
Code, 20 lines
# n xref sections chained by /Prev, each inside a string of the trailer before it,
# with a pad of `a` bytes in the innermost string.
import sys
n, pad = int(sys.argv[2]), int(sys.argv[3]) if len(sys.argv) > 3 else 1 << 20
out = bytearray(b"%PDF-1.7\n"); offs = []
for i, o in enumerate([b"<< /Type /Catalog /Pages 2 0 R >>", b"<< /Type /Pages /Kids [3 0 R] /Count 1 >>",
                       b"<< /Type /Page /Parent 2 0 R /MediaBox [0 0 100 100] >>"], 1):
    offs.append(len(out)); out += b"%d 0 obj\n%s\nendobj\n" % (i, o)
table = b"xref\n0 4\n0000000000 65535 f \n" + b"".join(b"%010d 00000 n \n" % o for o in offs)
first = len(out)
for i in range(n):
    out += table + b"trailer\n<< /Size 4 /Root 1 0 R "
    if i + 1 < n:
        prev = len(out) + len(b"/Prev 0000000000 /S (")
        out += b"/Prev %010d /S (" % prev
    else:
        out += b"/S ("
out += b"a" * pad + b") >>\n" * n
out += b"startxref\n%d\n%%%%EOF\n" % first
open(sys.argv[1], "wb").write(out)

Cause. populate_from_xref_table parses each section's trailer dictionary in full (xref.rs, read_xref_table_trailer). It then follows its /Prev and /XRefStm (xref.rs), up to MAX_XREF_CHAIN_DEPTH = 256 sections (xref.rs). Nothing stops a section from lying inside the previous trailer, for example in a string, and each trailer parse then lexes everything nested below it.

Fix. Valid files never nest sections. So a /Prev or /XRefStm offset that falls inside bytes already read for another section of the chain could be treated as damage and sent to the rebuild, which reads this file in linear time. My fork reads the sections on disjoint bytes this way, as part of a larger change (f8384eb); happy to open a small PR for main.

Reproduction. The generator below writes an object stream whose table lists objects 5 to N + 4 all at offset 0, where the one member is << /A [5 0 R 6 0 R ...] >>; the page uses object 5 as an ExtGState. extract_pages_to_pdf(&pdf, &[0]) on main at 036fb21c:

Generator (python3 gen.py out.pdf N)
Code, 24 lines
# An object stream whose member table lists objects 5 .. 5+n-1 all at offset 0, where one
# dictionary refers to all n of them; the page uses object 5 as an ExtGState.
import sys
n = int(sys.argv[2])
nums = range(5, 5 + n)
member = b"<< /A [%s] >>" % b" ".join(b"%d 0 R" % k for k in nums)
header = b"".join(b"%d 0 " % k for k in nums)
body = header + member
out = bytearray(b"%PDF-1.7\n"); offs = {}
def obj(num, data):
    offs[num] = len(out); out.extend(b"%d 0 obj\n%s\nendobj\n" % (num, data))
obj(1, b"<< /Type /Catalog /Pages 2 0 R >>")
obj(2, b"<< /Type /Pages /Kids [3 0 R] /Count 1 >>")
obj(3, b"<< /Type /Page /Parent 2 0 R /MediaBox [0 0 100 100] /Resources << /ExtGState << /G 5 0 R >> >> >>")
obj(4, b"<< /Type /ObjStm /N %d /First %d /Length %d >>\nstream\n%s\nendstream" % (n, len(header), len(body), body))
size = 5 + n + 1
xref_num = size - 1
offs[xref_num] = len(out)
rows = [(0, 0, 0xFFFF), (1, offs[1], 0), (1, offs[2], 0), (1, offs[3], 0), (1, offs[4], 0)]
rows += [(2, 4, i) for i in range(n)] + [(1, offs[xref_num], 0)]
data = b"".join(bytes([t]) + a.to_bytes(4, "big") + b.to_bytes(2, "big") for t, a, b in rows)
out += b"%d 0 obj\n<< /Type /XRef /Size %d /W [1 4 2] /Root 1 0 R /Length %d >>\nstream\n" % (xref_num, size, len(data))
out += data + b"\nendstream\nendobj\nstartxref\n%d\n%%%%EOF\n" % offs[xref_num]

vello vello_cpu: multi-threaded flush busy-waits on try_recv while the workers finish
Fix in our fork a0fd8ba5

With num_threads > 0, RenderContext::flush busy-waits for the workers. The calling thread stays at 100 % CPU for as long as the workers need to finish.

Reproduction. Linux only, because it reads /proc/thread-self/schedstat. Pass the thread count as the argument.

Code, 50 lines
// vello_cpu with features ["std", "u8_pipeline", "multithreading"]
use std::time::Instant;
use vello_cpu::color::{AlphaColor, Srgb};
use vello_cpu::kurbo::{BezPath, Point};
use vello_cpu::{Pixmap, RenderContext, RenderSettings, Resources};

/// CPU time of the calling thread, in ms.
fn thread_cpu_ms() -> f64 {
    let s = std::fs::read_to_string("/proc/thread-self/schedstat").unwrap();
    s.split_whitespace().next().unwrap().parse::<f64>().unwrap() / 1e6
}

fn main() {
    let threads: u16 = std::env::args().nth(1).map_or(8, |s| s.parse().unwrap());
    let mut seed = 1u64;
    let mut rand = || {
        seed = seed.wrapping_mul(6364136223846793005).wrapping_add(1442695040888963407);
        (seed >> 11) as f64 / (1u64 << 53) as f64
    };
    let paths: Vec<(BezPath, AlphaColor<Srgb>)> = (0..20_000)
        .map(|_| {
            let (cx, cy, r) = (rand() * 2000.0, rand() * 2000.0, 20.0 + rand() * 200.0);
            let at = |a: f64, r: f64| Point::new(cx + r * a.cos(), cy + r * a.sin());
            let mut p = BezPath::new();
            p.move_to(at(0.0, r));
            for i in 1..40 {
                let a = i as f64 / 40.0 * std::f64::consts::TAU;
                p.quad_to(at(a - 0.05, r), at(a, if i % 2 == 0 { r } else { 0.4 * r }));
            }
            p.close_path();
            (p, AlphaColor::new([rand() as f32, rand() as f32, rand() as f32, 0.5]))
        })
        .collect();
    let settings = RenderSettings { num_threads: threads, ..Default::default() };
    let mut ctx = RenderContext::new_with(2000, 2000, settings);
    for round in 0..4 {
        ctx.reset();
        for (path, color) in &paths {
            ctx.set_paint(*color);
            ctx.fill_path(path);
        }
        let (wall, cpu) = (Instant::now(), thread_cpu_ms());
        ctx.flush();
        let (wall, cpu) = (wall.elapsed().as_secs_f64() * 1e3, thread_cpu_ms() - cpu);
        ctx.render(&mut Pixmap::new(2000, 2000), &mut Resources::new());
        if round > 0 {
            println!("num_threads={threads}: flush took {wall:.0} ms, of which the calling thread was on CPU {cpu:.0} ms");
        }
    }
}

Measurement. AMD Ryzen 9 9950X (16 cores, 32 threads), Linux, release build, vello_cpu features std, u8_pipeline, multithreading. Scene: 20 000 semi-transparent 40-point stars with quadratic edges on 2000 × 2000. Three runs per row after a warm-up, on main 235739c4 (multi_threaded.rs is unchanged on 7d70631a). "Blocking recv" is main with the fix below.

num_threads = 8 (the default on this machine) 58–65 ms 58–65 ms 62–63 ms 32–34 ms
num_threads = 2 251–257 ms 250–255 ms 256–260 ms 49–52 ms

  • With idle cores, the loop costs a core for the length of flush.
  • When cores are short, it takes CPU time from the workers it waits for, and flush gets slower.
  • The default num_threads is min(available_parallelism - 1, 8). So on a machine with up to 9 hardware threads, the workers plus the waiting thread already fill every core, and any other load makes them compete.

Cause (main 7d70631a). MultiThreadedDispatcher::record_finished_commands polls the result channel with try_recv in a loop. On TryRecvError::Empty, its Empty arm loops again and returns only when abort_empty is true. flush calls it with abort_empty = false.

Cause. - SingleThreadedDispatcher::push_layer generates the layer clip's strips with existing_clip.map(|clip| clip.path), i.e. intersected with the active clip path; pop_layer composites through them. With no layer clip, nothing of the clip path reaches the composite. - The multi-threaded worker does the same with path_clip. - The fills inside the layer go through the active clip path as usual (fill_path).

use std::sync::Arc;
use vello_cpu::kurbo::{Affine, Rect};
use vello_cpu::peniko::{color::PremulRgba8, Extend, ImageQuality, ImageSampler};
use vello_cpu::{Image, ImageSource, Pixmap, RenderContext, RenderSettings, Resources};

fn main() {
    let img_w: u16 = 16384;
    let mut source = Pixmap::new(img_w, 1);
    for (i, p) in source.data_mut().iter_mut().enumerate() {
        let v = (i % 251) as u8; // the picked texel is known up to multiples of 251
        *p = PremulRgba8 { r: v, g: v, b: v, a: 255 };
    }
    let source = Arc::new(source);
    for scale in [0.737f64, 1.3] {
        for width in [512u16, 1024, 2048, 4096, 8192, 12000] {
            let settings = RenderSettings { num_threads: 0, ..Default::default() };
            let mut ctx = RenderContext::new_with(width, 4, settings);
            ctx.set_transform(Affine::scale(scale));
            ctx.set_paint(Image {

                sampler: ImageSampler {
                    x_extend: Extend::Pad,
                    y_extend: Extend::Pad,
                    quality: ImageQuality::Low,
                    alpha: 1.0,
                },
            });

            ctx.flush();

            ctx.render(&mut pixmap, &mut Resources::new());

    }
